Quick start

  1. Copy your connection from the cabinet.
  2. Get a ref and definition for each asset you give or accept.
  3. Publish an intent with amounts, conditions and your receiving details: one request, the reply is the outcome.
  4. If the reply is lost, read your intents before sending it again.
  5. Read your tickets and make your transfers using the supplied payment details.

1. Connect

The account owner creates an API key in the cabinet and copies the connection:

MULTIPISTON_NODE_URL=https://…
MULTIPISTON_PERSONA_ID=<participant from the connection>
MULTIPISTON_API_KEY=mpk1.…

Send Authorization: Bearer <MULTIPISTON_API_KEY> with API requests. Use the participant from the same connection as persona_id. Keep the key out of URLs, logs and shared chats. Replacing or disabling a key in the cabinet stops its previous connections.

Use a distinct x-request-id for each concurrent request to the node: 1–128 letters, digits or ._-. Send withdrawal to the node that published the intent.

What the key can do

A key can publish and withdraw intents and read its own intents and tickets. The account owner manages the key, plan, markets and invitations in the cabinet. All connections share the account's plan limits.

2. Prepare assets

Every asset you give or accept needs a ref containing chain and token, and its corresponding definition. Obtain both from a catalog entry, a recipe, or the asset builder. You can use an asset without adding it to the catalog.

Amounts are positive whole numbers of the definition's unit, written as strings without leading zeros. For example, 1.5 kg with unit: "g" is "1500". The largest amount is 340282366920938463463374607431768211455. A Unique asset always has amount "1".

Use the catalog

Browse the catalog or load catalog.json with the SDK. The SDK checks the entries and recipes it loads. Stop if loading fails or dropped is not empty.

Every release is signed. Check catalog.json against /catalog/catalog.json.minisig with the Multipiston public key RWQAC4QC/Z9aCZXzn3uizdnX/J3kEAEzAWU+UjCjVtQ9znjCn2OeGTj3: minisign -Vm catalog.json -P RWQAC4QC/Z9aCZXzn3uizdnX/J3kEAEzAWU+UjCjVtQ9znjCn2OeGTj3.

import { loadCatalog } from "@multipiston/catalog";

const response = await fetch("https://<site>/catalog/catalog.json");
if (!response.ok) throw new Error("Catalog unavailable");
const catalog = loadCatalog(await response.json());
if (catalog.dropped.length) throw new Error("Catalog could not be loaded in full");

const usd = catalog.assets.find(asset =>
  asset.id === "usd" && asset.status === "listed");
if (!usd) throw new Error("USD entry unavailable");
// Use usd.ref and usd.definition in the intent.

For a new intent, use only entries with status: "listed". An entry marked retired is for earlier tickets; use its replaced_by entry when provided. Keep the entry's reference and definition together. Choose crypto assets by network as well as name; a symbol alone does not identify the asset.

Use a recipe

A recipe prepares an asset from values such as a currency, location, product code or delivery period. Choose a recipe in the catalog, fill in its parameters, and use the resulting definition and reference. The asset builder provides the same form.

const built = catalog.build("money.cash.banknotes", {
  currency: "EUR",
  city: "DEBER"
});
if (!built.ok) throw new Error("Check these fields: " + built.invalid.join(", "));
// Use built.ref and built.definition.

Choose list options by their id. Supply other values in the form requested by the recipe, such as an ISIN or a period label. Amounts use the resulting definition's unit. For regulated assets, trade only where you and your counterparty may do so.

Describe your own asset

If no entry or recipe fits, use Build an asset → “Any asset”, or prepare the definition with the SDK:

import { deriveAsset, sortTerms } from "@multipiston/catalog";

const myDefinition = {
  version: 1,
  domain: "other.custom",
  instrument: "widget-7",
  source: "spec:acme",
  kind: "Fungible",
  unit: "item",
  terms: sortTerms([{ key: "colour", value: "red" }])
};
const myRef = deriveAsset(myDefinition);
// Use myRef together with myDefinition. Fix the definition if the SDK rejects it.
FieldWhat to supply
version1
domainThe family's domain, or other.custom when no family fits.
instrumentThe item, model, service or right being offered.
sourcespec:<standard> for a standard item; issuer:<domain> for a company's obligation; registry:<registry> for a registered right.
kindFungible for interchangeable units; Unique for a particular item.
unitThe smallest delivery unit, such as g, item or hour. Use a catalog unit where one fits.
termsEssential fixed properties as {key, value} pairs. Each key occurs once. Use the builder or SDK to prepare them.

Use these fields when the asset needs a place, route, time or capacity. Supply every field in a group together; each identifier in the last row can be used on its own.

PropertyTerm keys
Placemp.place_authority, mp.place_id
Routemp.origin_authority, mp.origin_id, mp.destination_authority, mp.destination_id
Delivery periodmp.start_us, mp.end_us
Start windowmp.start_window_from_us, mp.start_window_to_us
Completion deadlinemp.provision_complete_by_us
Capacitymp.capacity_unit, mp.concurrent_units
Identifiersmp.configuration_id, mp.resource_id, mp.object_id, mp.object_version, mp.meter_id, mp.package_id

Place, route, capacity unit and identifiers must not be empty. Times are UTC POSIX microseconds, written as whole numbers without leading zeros, no greater than 9223372036854775807. A period or start window must begin before it ends; a start window must lie within the delivery period. The completion deadline must be at or after the period's end and after the start window opens. mp.concurrent_units must be positive.

Your own property keys use lower-case Latin letters, digits and _; the mp. prefix is reserved. Keep prices, trade amounts, payment details, credentials and random values out of the definition. Identify a particular off-chain item with Unique and mp.object_id. Another seller of the same standard good does not create a different asset; a different specification or issuer obligation does.

Crypto assets

Use the catalog entry for the required network when available. For an unlisted asset, use its CAIP-19 identifier in instrument, source: "spec:caip19", unit: "atom" and terms: [], then obtain the reference with the SDK.

AssetDomainInstrument example
Native coincrypto.coineip155:1/slip44:60
Tokencrypto.tokeneip155:1/erc20:0xa0b86991c6218b36c1d19d4a2e9eb0ce3606eb48
NFTcrypto.nfteip155:1/erc721:<contract>/<id>
Multi-tokencrypto.multi-tokeneip155:1/erc1155:<contract>/<id>

Use lower-case EVM addresses and decimal token IDs without leading zeros. An ERC-721 NFT is Unique; an ERC-1155 ID is Fungible. Amounts are in the asset's smallest unit. The same named token on different networks is a separate asset: list every acceptable network asset in want_any_of and provide a receiving route for each.

Currencies

Use the currency's catalog entry. Bank-transfer amounts are in the currency's minor unit: "100" USD is one dollar; currencies without minor units, such as JPY, use whole currency units. Put bank or other receiving details in receive_routes, not in the currency definition.

Use the asset reference

Copy the full {chain, token} from the entry, builder or SDK result without editing it. Use it in the intent and receiving routes, and include its definition in asset_definitions. Keep references and definitions as a pair.

SDK

Use @multipiston/catalog to load the catalog, build recipe assets and prepare your own asset references as shown above. Get the package from a catalog release. For display amounts, toAtoms("12.5", 3) returns "12500"; a result of null means the input is invalid or too precise. Import toAtoms from the same package.

3. Publish an intent

The request

Use the assets prepared above. Send POST {MULTIPISTON_NODE_URL}/api/v1/submit-offer with Content-Type: application/json and your authorization header:

const body = {
  offer_fdl: JSON.stringify({
    type: "Formula/Offer",
    fdl_schema: "schema:agnostic",
    have: { type: "Asset", ...myRef, amount: "5" },
    want: { type: "Asset", ...usd.ref, amount: "200" },
    constraints: { min_fill_ppm: 500000, slippage_ppm: 0 }
  }),
  persona_id: MULTIPISTON_PERSONA_ID,
  market_scope: { kind: "global" },
  asset_definitions: [myDefinition, usd.definition],
  receive_routes: [{
    ...usd.ref,
    destination: { profile: "OpaqueUtf8", text: "<your USD receiving details>" }
  }]
};
// Send JSON.stringify(body) with Content-Type: application/json
// and Authorization: Bearer <MULTIPISTON_API_KEY>.

Set the assets and amounts in have and want. Include each asset's definition once in asset_definitions, and your receiving details for each accepted asset in receive_routes. Send exactly these five fields: the node refuses any other.

InputAccepted values
min_fill_ppmMinimum accepted share: 50000 to 1000000 in steps of 50000. 500000 is 50 %.
slippage_ppmPermitted price difference: 0 to 1000000. 0 uses the stated price.
want_any_of (optional)Up to 64 additional accepted assets inside constraints; each has type: "Asset", chain, token and amount.
market_scope{"kind":"global"}, or {"kind":"private","market_id_hex":"<your market reference>"}.

Publish

One request publishes the intent; the reply is its outcome:

ReplyAction
200 with ok: truePublished. Save offer_intent and publication_receipt.publication_ref_hex: a withdrawal names both.
4xx with ok: falseRefused before taking effect. Read error and, when present, admission_refusal.cause; correct the request or retry later as the status says.
503, or a lost replyThe outcome is unknown. Read your intents before sending the same request again; a second request for an intent that is already published is refused with intent_live.

Change an intent

An intent is not replaced or renewed in place. To change its conditions, definitions or receiving details, withdraw it, then publish the new one.

Withdraw

Send POST {MULTIPISTON_NODE_URL}/api/v1/withdraw-offer to the node that published it:

{"intent":"<intent reference>","persona_id":"<participant>","market_scope":{"kind":"global"},"expected_publication_ref_hex":"<publication reference>"}
ReplyMeaning
{"ok":true,"withdraw":{"fate":"removed"}}The publication is withdrawn.
{"ok":true,"withdraw":{"fate":"superseded","current":"<publication reference>"}}A newer publication of the intent is current. Read it before withdrawing it.

On a conflict, read the intent before retrying. If the reply is lost or the service is unavailable, repeat the same withdrawal or read your intents.

4. Read intents and tickets

Read central_url from GET {MULTIPISTON_NODE_URL}/api/v1/status. Use that address for these requests, with the same authorization header:

RequestUse
GET /central/offers?limit=1…64[&cursor=…]List your intents by issue number: each row is offer_seq, intent and market_scope. Send next_cursor as cursor for the next page; null marks the end.
GET /central/offers/{offer_seq}Read one intent by its offer_seq: assets, definitions, publication reference and lease. A published intent has lease_state: "Active" with lease_until, market_clock and lease_span — lease_until − market_clock is what is left of it. lease_state: null means the intent is not in the book right now (on its way in or out). Another account's or unknown number returns 404.
GET /central/execs[?limit_u16=1…256][&cursor=…][&since=…]List your tickets, newest first. A first page (no cursor) carries head: save it. Send continuation.cursor as cursor for the next page; range_exhausted marks the end. Later, since=<head> returns only the tickets written after it, with a new head.
GET /central/execs/{exec_id_hex}Read your outgoing transfers: asset, amount_atoms, destination and definition. Use the supplied recipient and payment details.

Treat all returned intent, publication, market, ticket and pagination references as values to save and send back unchanged.

Events of your key

Instead of polling, follow your key's events. Take a ticket with POST {central_url}/ws/ticket (empty body, the same authorization header) — the reply is {"ticket","expires_in_ms"}; at most 10 tickets in 60 seconds, then 429 ws_ticket_rate_limited with retryAfterMs and Retry-After. Connect wss://<central host>/ws with Sec-WebSocket-Protocol: metaphora-v2, <ticket> before the ticket expires, and send an Origin header equal to one of the deployment's allowed addresses — the cabinet's address. Without it the connection is refused 403 before it opens.

Event or closeAction
FinancialViewsChanged {exec_id_hex}A ticket of yours was written: read GET /central/execs?since=<head>.
ApiAccessChanged {generation}Your key was issued, replaced or disabled in the cabinet.
Close 4001Take a new ticket, reconnect and read your tickets with since: a key's socket does not resynchronise in place.
Close 4003 key_revokedThe key was replaced or disabled: ask the owner for the current one.
Close 1013 or 1011Wait, then take a new ticket.

Events arrive in frames {"type":"batch","items":[{"c":…,"e":<event>}],…}; an event says what to read, the reads are the truth.

5. Handle errors

ResponseAction
400 or 422Correct the request or asset fields before retrying.
401Ask the owner for a current key.
403Check the participant, market access and plan limit.
409Read the current publication before withdrawing again. For a request ID conflict, use a distinct request ID.
429Retry later and respect Retry-After when present.
412 or 503Retry later. After a publication, read your intents before sending it again; for withdrawal, repeat the same withdrawal.

Inspect error and admission_refusal when present. A transport error after a publication does not establish whether it was published: read your intents before taking another action.

Every error is one of a closed list: busy, central_unavailable, conflict, not_found, invalid_request, unsupported_client, unauthorized, not_allowed, storage_full, resident_capacity, root_capacity, market_member_capacity, billing_capacity, device_key_capacity, session_capacity, login_replay_quota, login_rate_limited, ws_ticket_rate_limited; the node adds rpc_correlation_conflict, invalid_relay_response, node_unavailable and fdl_canon_error; ticket reads add invalid_limit, invalid_cursor, invalid_since, invalid_exec_id_hex, exec_not_found, exec_binding_invalid and fcap_unsupported_version (409: a ticket record of another version). admission_refusal.cause is one of: node_rpc_pending_capacity, node_rpc_target_mailbox_full, node_rpc_command_credit_capacity, node_rpc_allocation_pressure, node_rpc_target_resolution_incomplete, node_strategist_admission_capacity, node_submit_owner_capacity, root_offer_limit_exceeded, segment_registry_domain_capacity, segment_registry_resident_bytes_capacity, segment_registry_allocation_pressure, node_withdraw_owner_capacity, session_auth_mailbox_full, dpop_lookup_mailbox_full, dpop_lookup_key_capacity, dpop_lookup_waiter_capacity, dpop_lookup_total_waiter_capacity, target_publication_pending, cell_row_allocation_pressure, owner_binding_conflict, target_in_plan, intent_live, market_closed. The status and error decide what to do; the cause only details it.

7. Transfers

Multipiston provides intents and tickets. It does not hold funds, issue assets or perform transfers. Check the assets, quantities and recipients in your ticket and carry out your outgoing transfers yourself. Describing an asset does not reserve stock, establish ownership or confirm delivery.
